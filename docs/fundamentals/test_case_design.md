# 測試案例設計

測試案例（Test case）剛開始寫會覺得不難寫，但等到案例 review 之後可能會發現漏了不少東西。

到底怎麼設計測試案例呢？

開發有 Design Pattern，那測試案例的設計有沒有 Pattern 呢？

其實在測試工作中，也確實有許多反覆出現的問題，以及一套可以拿來處理這些問題的測試設計技術。

下面就來介紹一些測試設計的技巧。

## 使用案例／情境測試（Use Case / Scenario Testing）

根據使用者的行為流程來設計測試案例的方法，重點在於驗證系統在真實業務場景中的完整行為。

一個 Use Case 可能包含：

* 使用者（Actor）：誰在使用系統？
* 目標（Goal）：他想完成什麼？
* 前置條件（Precondition）：開始之前需要滿足什麼條件？
* 主流程（Main Flow）：正常情況下怎麼完成？
* 替代流程（Alternate Flow）：有哪些流程上會遇到的分支？
* 例外流程（Exception Flow）：發生錯誤時會怎麼處理？
* 後置條件（Postcondition）：完成後系統應該處於什麼狀態？

以「使用者登入」為例子：

> Use Case：登入
> 
> 
> 使用者：
>     已註冊使用者
> 
> 目標：
>     使用者成功登入系統
> 
> 前置條件：
>     使用者已經註冊帳號
> 
> 主流程：
> * 開啟登入頁面 → 輸入帳號與密碼 → 點擊登入 → 系統驗證帳密 → 登入成功
> 
> 替代流程：
> * 使用者選擇使用 Google 登入
> * 使用者選擇使用 Apple 登入
> 
> 例外流程：
> * 帳號不存在
> * 密碼錯誤
> * 帳號被鎖定
> * 密碼已過期
> 
> 後置條件：
> * 使用者成功登入 Session

這些流程都可以進一步轉換成測試案例，例如：

| 情境          | 預期結果   |
| ----------- | ------ |
| 正確帳號 + 正確密碼 | 登入成功   |
| 正確帳號 + 錯誤密碼 | 登入失敗   |
| 使用者選擇使用 Google 登入 | 登入成功   |
| 使用者選擇使用 Apple 登入 | 登入成功   |
| 不存在的帳號      | 顯示錯誤   |
| 被鎖定的帳號      | 無法登入   |
| 密碼已過期       | 要求更新密碼 |


使用案例／情境測試的重點是 **從使用者的目標出發，確認主要流程、替代流程與例外流程是否都能正確完成。**

使用案例關注的不只是某個元件或功能是否正常，而是**不同功能串在一起後，使用者是否真的能完成一個完整的任務**。

## 等價類劃分（Equivalence Partition）

當輸入有大量可能值時，不需要每一個值都測試。

如果一群輸入值在系統中會產生相同的行為，就可以將它們視為等價類別，從每個類別選擇一個代表值進行測試即可。

例如年齡限制為 18～65 歲：

| 年齡 | 結果 |
|---|---|
| 小於 18 | 無效 |
| 18～65 | 有效 |
| 大於 65 | 有效 |

因此不需要逐一測試 1、2、3、4、5⋯⋯17、18、19、20⋯⋯65、66、67、68⋯⋯


而可以先選擇：

* 17 → 無效類別
* 30 → 有效類別
* 66 → 無效類別

等價類劃分的核心是：**把大量的輸入分成具有代表性的群組，降低測試案例數量。**

### 邊界值分析（Boundary Value Analysis）

錯誤經常發生在「剛好可以」與「剛好不可以」的地方，因此除了測試等價類別，也需要特別關注邊界。

延續年齡 18～65 歲的例子：

```
17 → 無效
18 → 有效
19 → 有效

64 → 有效
65 → 有效
66 → 無效
```

也就是特別關注**邊界值-1、邊界值、邊界值 + 1**。

邊界值乍看會以為只是數值，不過數值可是包山包海，常見的包括：

* 字串長度
* 檔案大小
* 日期範圍
* 筆數限制
* 欄位數量
* 分頁數量

等等等

核心概念是：**刻意測試限制的邊界。**

### 決策表測試（Decision Table Testing）

當系統行為取決於「多個條件的組合」時，可以使用決策表整理規則。

用複雜的租車折扣業務邏輯當範例，假設今天有一產品規則如下：

1. 未發生過事故才能享有優惠。
1. 駕駛人的年齡滿 25 歲，為女性，提供 10% 的折扣。
1. 符合上述條件，並登記12歲以下孩童為乘客，再折 100 元。
1. 駕駛人的年齡滿 25 歲，為男性，未發生過事故，並有登記12歲孩童為乘客，可折 100 元。

這個業務邏輯包含多個條件的組合，而且不同條件可能觸發不同的優惠，結果也可能同時成立並疊加。

因此，很適合使用決策表測試，系統化整理條件組合與對應的動作：

（T 代表 True，符合條件；F 代表 False，未符合條件；Y 代表 Yes，可獲得折扣；N 代表 No，不可獲得折扣）

| **條件／輸入** | **組合 1** | **組合 2** | **組合 3** | **組合 4** | **組合 5** | **組合 6** | **組合 7** | **組合 8** | **組合 9** | **組合 10** | **組合 11** | **組合 12** | **組合 13** | **組合 14** | **組合 15** | **組合 16** |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 年齡 >= 25 歲    | T | T | T | T | T | T | T | T | F | F | F | F | F | F | F | F |
| 女性駕駛         | T | T | F | F | T | T | F | F | T | T | F | F | T | T | F | F |
| 未發生過事故      | T | T | T | T | F | F | F | F | T | T | T | T | F | F | F | F |
| 有登記孩童       | T | F | T | F | T | F | T | F | T | F | T | F | T | F | T | F |
| **動作／輸出**   | | | | | | | | | | | | | | | | |
| 折 100 元       | Y | N | Y | N | N | N | N | N | N | N | N | N | N | N | N | N |
| 10% 折扣        | Y | Y | N | N | N | N | N | N | N | N | N | N | N | N | N | N |

用決策表展開所有可能的組合，也可以幫助我們檢查規格是否存在矛盾、遺漏或未定義的情況。

另外，從上面的決策表我們也能發現，某些條件一旦成立或不成立，就已經足以決定結果，此時其他條件便不再影響該決策規則，可以使用 - 表示「不關心」，進一步合併規則，減少不必要的測試組合。

比如這個例子中，「未發生過事故」與「年齡 >= 25 歲」都是享有優惠的必要條件：

一旦發生過事故，就不會有任何折扣，其他條件的變化都不需要關心。
年齡未滿 25 歲，也不會有任何折扣，其他條件的變化同樣不需要關心。

因此，我們可以進一步收斂出代表性的決策規則：

（「-」代表該條件不影響決策；若實務上需要記錄詳細測試結果，可再將「-」展開為不同的實際條件組合。）

| **條件／輸入** | **組合 1** | **組合 2** | **組合 3** | **組合 4** | **組合 5** | **組合 6** |
|---|---|---|---|---|---|---|
| 年齡 >= 25 歲    | T | T | T | T | F | - |
| 女性駕駛         | T | T | F | F | - | - |
| 未發生過事故      | T | T | T | T | - | F |
| 有登記孩童       | T | F | T | F | - | - |
| **動作／輸出**   | | | | | |
| 折 100 元       | Y | N | Y | N | N | N |
| 10% 折扣        | Y | Y | N | N | N | N |

這樣可以將原本 16 種條件組合，收斂成 6 個具有代表性的決策規則，同時保留各種不同的業務結果。

### 狀態轉換測試

有些系統的行為不只取決於「現在輸入了什麼」，還取決於**系統目前處於什麼狀態**。

例如帳號：

```
正常
 ↓ 登入失敗
登入失敗 1 次
 ↓ 登入失敗
登入失敗 2 次
 ↓ 登入失敗
登入失敗 3 次
 ↓
鎖定
```

這時候測試的重點就不只是：

> 「輸入錯誤密碼會怎樣？」

而是：

> 「在不同狀態下輸入錯誤密碼，系統會怎麼轉換？」

因此可以針對：

* 狀態
* 觸發事件
* 狀態轉換
* 轉換後的行為

設計測試。

常見應用包括：

* 訂單狀態
* 帳號狀態
* 付款狀態
* 工作流程
* Session
* 網路連線狀態

### 配對測試

當系統有很多測試參數時，所有組合可能會快速增加。

例如：

```
瀏覽器 × 作業系統 × 裝置 × 語言
```

如果每個參數都有多個選項，完整測試所有組合可能會產生大量測試案例。

**配對測試（Pairwise Testing）** 的概念是：

> **讓任意兩個參數的值組合，都至少被測試一次。**

例如：

```
Browser × OS × Device
```

不一定需要測試所有可能組合，而是透過演算法選出較少的測試組合，同時涵蓋兩兩參數之間的組合。

它適合處理：

* 瀏覽器
* 作業系統
* 裝置
* 語言
* 設定
* API 參數

等具有大量組合的測試情境。

需要注意的是，Pairwise 並不是「測試兩個條件就好」，而是**以兩兩組合的覆蓋為目標降低測試案例數量**。

### 錯誤猜測

有些缺陷很難單純從需求規格推導出來。

這時可以利用過往的測試經驗、歷史缺陷與對系統的理解，主動猜測：

> **「這裡以前很容易出問題，那我應該怎麼測？」**

例如表單欄位可能會特別嘗試：

```
空值
空白
超長字串
特殊字元
Unicode
負數
極大數字
異常格式
```

又或者針對系統行為測試：

```
重複點擊
快速連續操作
Session 過期
網路中斷
重複送出 Request
重新整理頁面
```

錯誤猜測不是毫無根據地「亂猜」，而是利用：

* 過往缺陷
* 常見錯誤模式
* 系統特性
* 技術經驗
* 開發實作方式

來找出可能被其他測試技術忽略的缺陷。

它的價值就在於：

> **規格告訴你系統「應該怎麼運作」，經驗則可以幫你思考「它可能在哪裡壞掉」。**
